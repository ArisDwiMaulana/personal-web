Automating Linux Server Hardening with Ansible and CIS Benchmarks

AP
Adrian Pratama
24 Oktober 2025 · 8 menit baca

Deploying bare-metal or cloud instances using default distribution templates presents an immediate attack surface. Standard Linux installations typically ship with promiscuous network daemon defaults, excessive file permissions, and permissive authentication schemes. Leaving an exposed production host unhardened is simply negligence.

Manual host fortification across a fleet of tens or hundreds of machines quickly introduces human error and operational drift. By encoding the Center for Internet Security (CIS) Benchmark recommendations into immutable, idempotently executed Ansible playbooks, security baselines transition from passive documentation into automated CI/CD guardrails.

01. Prerequisites & Architecture Setup

Before executing remediations, verify your Ansible management controller has unrestricted SSH root access or passwordless sudo capability over target clusters running Debian 12 or Ubuntu 22.04 LTS. We begin by pulling community-audited CIS modules from Galaxy:

Bash
$ ansible-galaxy install dev-sec.os-hardening dev-sec.ssh-hardening

02. Writing the Hardening Playbook

Construct an orchestration playbook that applies kernel parameters (sysctl), restricts filesystem permissions, locks down SSH crypto suites, and purges obsolete packages. Notice how we enforce strict Ed25519 authentication and disable protocol fallback:

playbooks/cis_hardening.yml 
---
- name: Execute CIS Level 1 Linux Server Remediation
  hosts: production_nodes
  become: yes
  vars:
    os_security_users_allow: ["deployer", "secops"]
    ssh_server_password_authentication: no
    ssh_permit_root_login: "no"
    sysctl_overwrite:
      net.ipv4.conf.all.accept_redirects: 0
      net.ipv4.conf.all.send_redirects: 0
      fs.suid_dumpable: 0

  roles:
    - dev-sec.os-hardening
    - dev-sec.ssh-hardening
info

Catatan Mitigasi Akses SSH

Mengatur ssh_permit_root_login: "no" dan mewajibkan public key dapat langsung memutus akses jika SSH key deployer belum terpasang di ~/.ssh/authorized_keys. Disarankan selalu menguji perubahan pada lingkungan staging sebelum deployment produksi.

03. Audit & Verification with Lynis

Hardening without deterministic validation is merely wishful thinking. After the Ansible playbook runs across target instances, run lynis audit system to generate an objective compliance index score. Below is an excerpt from the audit execution terminal:

Hasil Audit Lynis CIS Benchmark Compliant (82/100)
[+] Menjalankan pemeriksaan SSH Server Configuration...
SSH Daemon running OK
PermitRootLogin disabled OK
PasswordAuthentication disabled OK
[+] Menjalankan pemeriksaan Kernel Hardening (sysctl)...
net.ipv4.ip_forward = 0 OK
fs.suid_dumpable = 0 OK

04. Key Takeaways & Operational Tips

  • check_circle Idempotency is mandatory: Your hardening playbooks must be safe to execute multiple times without restarting services unnecessarily or overwriting valid configuration deltas.
  • check_circle Baseline vs. Application Coexistence: Strictly separate OS base layer hardening from application runtime requirements (e.g., Elasticsearch needs high max_map_count).
  • check_circle Continuous Drifts Monitoring: Schedule weekly non-intrusive Lynis audits via Cron or CI runners to detect unapproved manual drifts on server estates.
